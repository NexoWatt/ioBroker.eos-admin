# Controller integration environment for EOS 9.0.17

The controller runs are local, controlled integration tests of the actual packaged adapter and ioBroker controller 7.2.5. They are not customer-hardware, LAN discovery, mDNS, external-provider or physical-actuator tests. The standard `admin.0` process is not started by this harness; its retained database object is a recovery fixture.

The first unmodified environment attempt failed before any product test. The controller's npm installation invoked `os.networkInterfaces()`, which the executor denied with `ERR_SYSTEM_ERROR`, syscall `uv_interface_addresses`, errno 1. npm rolled back the installation; the test framework subsequently reported the missing `@iobroker/db-objects-jsonl`. Its setup helper had not propagated the preceding npm exit status. The failed log is retained separately and is not evidence of a successful integration run.

The setup-only preload `controller-loopback-environment.cjs` preserves normal `os.networkInterfaces()` results. It catches only EPERM / the observed errno 1 failure of the exact `uv_interface_addresses` syscall. Other errors are rethrown. Its fallback contains only `127.0.0.1` and `::1`, both marked internal. A documented synthetic locally administered loopback MAC avoids the controller's `ifconfig`/`ip link` fallback; neither that identity nor any resulting controller UUID describes customer equipment.

The preload additionally invokes the existing reviewed `test/fixtures/loopback-egress.cjs` only for the installed EOS process. That guard restricts adapter egress to loopback. Real TCP, HTTP, TLS and controller database operations remain in use. npm and controller setup are not mocked. Authentication, authorization, licenses, TLS verification and the packaged product code are unchanged. The HTTP integration fixture is explicitly configured for fresh manual setup as described below; no production default is changed.

- Existing source `test/fixtures/loopback-egress.cjs`: SHA-256 `45ec889e2d1c4434cc7a8e7007e4f3c1dd7e8999fc2f8d09d85285b887f4cd80`.

Each final run creates a fresh private 0700 directory under `/tmp` inside the same executing process, passes it through `TMPDIR` to the real harness and its children, and sets `npm_config_offline=true`. Parent-path ownership, permissions and symlink status are captured in `controller-node24-final-paths.json` / `controller-node22-final-paths.json` before starting. Logs and completion metadata are persisted separately under `setup-917`. A preliminary workspace-backed run was correctly rejected by the unchanged production storage guard because its `/workspace` ancestor was world-writable; its failed log remains separate. No shared directory permissions or product security checks were weakened. The exact controller 7.2.5 and JSONL database 7.2.5 upstream tarballs are present in the npm cache. An integrity check against the existing controller lock found 256 of 257 tarballs locally; the only unavailable tarball was optional macOS-only `fsevents@2.3.3`. Installed versions are not substituted. Node 24 uses its existing local header cache; Node 22 uses the headers in the locally available Node 22 distribution.

The authoritative completion records are the matching entries in `check-status.json`, written by `run-check.py`, with command, working directory, exit status, timestamps, log bytes and SHA-256. A run qualifies as passed for its executed scenarios only when its actual command exits 0 and its complete Mocha summary reports no failures. Pending scenarios must be reported explicitly and never counted as passed. The final planned result logs are `node24-controller-private-loopback-final.log` and `node22-controller-private-loopback-final.log`; this environment note alone asserts no test result.

The first private-directory run (`node24-controller-private-loopback-integration.log`) reached actual HTTPS tests but exposed an invalid old fixture assumption: it expected configuration saves before central license activation while leaving automatic migration enabled. The unchanged migration coordinator correctly fenced those saves with `EOS_MODULE_MIGRATION_BLOCKED`. The fixture now proves through the actual controller object database that there are zero instances for all four legacy sources, then explicitly selects fresh manual setup (`eosAutoMigrate:false`). Its real authenticated HTTP save scenario first asserts migration phase `DISABLED`, an invalid license with core operation disabled, and an inactive device module. It retains the positive save, session preservation, unchanged instance-object checks and asserts that saving a disabled draft does not activate the module or bypass activation. This scenario does not test automatic customer migration or a licensed operational cutover. Production defaults and migration/license gates are unchanged.

Two manufacturer-trust import scenarios are intentionally pending in this executor because `/` and `/etc` are owned by UID 1000 instead of POSIX root. The tests explicitly detect this exact limitation and verify the unchanged `TRUST_PERMISSIONS` rejection. These import scenarios need a separate normal root-owned host; neither a test-only ownership shim nor a production permission relaxation is used.
